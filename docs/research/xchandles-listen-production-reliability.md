# `xchandles listen` production reliability

Reviewed 2026-08-19 at commit `2b1d882`. Scope: local source, tests, and deployment examples. No live Coinset soak/load/fault-injection test was performed.

## Verdict

**Overall: 5/10 — usable as a supervised canary, but not reliable enough to be the sole source for spend-critical production decisions.**

The chain/indexing design is substantially better than a naive event listener: it replays registry history at startup, persists projections in SQLite, catches up followed NFTs, detects recent reorgs, rolls projections back, and refuses most chain-dependent API reads after the index becomes stale. The current implementation still has serious availability and integrity gaps: skipped peaks can permanently omit intermediate registry transitions, multi-registry results are matched by an order the upstream does not guarantee, projection write failures are logged and discarded, a block is not committed atomically, and reorg state is memory-only. Those gaps keep it below a strong production-readiness rating even though its functional test suite passes.

Suggested component ratings: chain/index correctness **5/10**, recovery/durability **5/10**, availability **5/10**, observability/operations **4/10**, API contract tests **8/10**.

## How it works

1. The CLI requires a comma-separated `--launcher-ids` value and optionally selects testnet11; otherwise it uses mainnet ([command definition](../../src/cli/commands.rs#L690), [dispatch](../../src/cli/commands.rs#L1571)). It selects the SDK's built-in Coinset endpoint for the chosen network ([client selection](../../src/cli/utils.rs#L198)), uses `data.db` in the current working directory, and creates its SQLite tables on startup ([database open/schema](../../src/cli/database.rs#L25)). `BIND_ADDR` controls HTTP binding and defaults to `0.0.0.0:8080` ([binding](../../src/cli/xchandles/listen.rs#L124)).
2. It constructs SQLite-backed singleton, handle-slot, registration, and pending-update stores, initializes freshness/pricing state, marks the index as resyncing, and spawns the HTTP API ([startup](../../src/cli/xchandles/listen.rs#L131)). The API exposes liveness, singleton/handle/registration/pending-transfer, expiration, price, and schedule reads ([routes](../../src/cli/xchandles/listener/api.rs#L112)); the legacy `/neighbors` endpoint is merged separately ([server setup](../../src/cli/xchandles/listen.rs#L221)).
3. Each connection cycle first walks every configured registry from its persisted tip (or launcher on cold start), saving chain state and collecting spent transitions ([sync walk](../../src/cli/xchandles/sync.rs#L49)). It then replays those transitions through the same projection path used for live spends, imports legacy persisted slots, and catches every followed NFT up to its current unspent coin in batches of 500 ([startup replay/catch-up](../../src/cli/xchandles/listen.rs#L463), [NFT catch-up](../../src/cli/xchandles/listen.rs#L394)).
4. It connects to Coinset's WebSocket and reacts to `peak` messages. On every peak it queries authoritative RPC state, resyncs spent registries, projects action logs and singleton changes, updates pricing/freshness, and deletes old spent slot/singleton cache rows every 30 minutes ([peak loop](../../src/cli/xchandles/listen.rs#L595), [transition projection](../../src/cli/xchandles/listen.rs#L360)).
5. A 32-peak `(height, header hash)` memory window detects recent forks; on a mismatch it rolls singleton, handle, registration/statistics, and pending-update projections back before resyncing registries ([detection](../../src/cli/xchandles/listen.rs#L849), [rollback](../../src/cli/xchandles/listener/index.rs#L556)). Chain-dependent reads fail with `index_stale` while resyncing/rolling back, more than 16 blocks behind, or more than 300 seconds since a successful peak ([freshness policy](../../src/cli/xchandles/listener/freshness.rs#L40), [API gate](../../src/cli/xchandles/listener/api.rs#L145)).

## Reliability findings

### What is strong

- **Restart recovery is designed in.** Registry history is resumed from persisted state, action logs are replayed, legacy slot-only databases have a migration fallback, and already-followed NFTs are walked until all current coins are unspent ([registry replay](../../src/cli/xchandles/listen.rs#L472), [fallback](../../src/cli/xchandles/listen.rs#L528), [catch-up loop](../../src/cli/xchandles/listen.rs#L399)).
- **The public API usually fails closed on stale chain data.** Startup sets `resyncing` before HTTP binds, and successful peak processing is what clears it ([startup gate](../../src/cli/xchandles/listen.rs#L189), [peak completion](../../src/cli/xchandles/listener/index.rs#L59)). This is an important protection against serving persisted state as current.
- **Recent reorg behavior is explicit and tested.** History retains recent states plus an older predecessor, and rollback covers all four projection families ([history policy](../../src/cli/xchandles/listener/store.rs#L137), [rollback implementation](../../src/cli/xchandles/listener/index.rs#L556)). Unit tests cover fork detection, while real-HTTP tests exercise singleton/handle/registration/pending-transfer rollback and stale responses ([fork tests](../../src/cli/xchandles/listen.rs#L881), [HTTP/reorg fixture](../../tests/listener_http.rs#L967)).
- **Deployment guidance has sensible perimeter controls.** The Docker example persists `/data`, runs unprivileged, and binds through a restart-managed container ([Dockerfile](../../Dockerfile#L18), [runner](../../run.sh#L10)); the Nginx example adds TLS, rate limiting, and short route-specific caching while avoiding caching stale/error responses ([Nginx guidance](../../xchandles-api-nginx.conf#L1)).

### Production risks

1. **Critical — skipped peaks can permanently omit registry transitions.** The live path parses logs only from the one currently tracked registry spend, then calls `sync_xchandles`, whose wrapper discards `spent_transitions`, and projects only the first logs ([live path](../../src/cli/xchandles/listen.rs#L716), [non-detailed wrapper](../../src/cli/xchandles/sync.rs#L38), [history walk](../../src/cli/xchandles/sync.rs#L129)). If an outage or skipped peak spans two or more registry spends, sync advances the persisted tip through all of them while handle/registration/pending projections for intermediate spends are never applied. A restart then resumes from the advanced tip, so it may not repair the omission.
2. **Critical for multiple launchers — response order is assumed but not guaranteed.** One batched `get_coin_records_by_names` response is enumerated and index `i` is used to select `registries[i]` ([association code](../../src/cli/xchandles/listen.rs#L703)). Chia's official `CoinStore.get_coin_records_by_names` accumulates results in a Python `set` and returns `list(coins)`, so request order is not an API guarantee ([official upstream implementation](https://github.com/Chia-Network/chia-blockchain/blob/main/chia/full_node/coin_store.py#L538-L558)). A reordered or partial response can sync/project the wrong configured registry.
3. **High — persistence/indexing errors can be silently accepted as a successful peak.** Store `upsert` methods return `()` and only print serialization/SQLite errors ([singleton example](../../src/cli/xchandles/listener/store.rs#L202), [handle example](../../src/cli/xchandles/listener/handle_store.rs#L245), [registration example](../../src/cli/xchandles/listener/registration_store.rs#L227)); transition discovery/follow failures are also only logged and the tip `on_block` result is discarded ([transition path](../../src/cli/xchandles/listen.rs#L360), [tip path](../../src/cli/xchandles/listen.rs#L779)). Peak processing can nevertheless call `note_peak` and mark the index fresh, serving incomplete or inconsistent data.
4. **High — a block transition is not atomic.** Registry coins/slots and each derived projection/statistics record are independent SQL statements; no transaction spans a transition ([registry writes](../../src/cli/xchandles/sync.rs#L139), [projection sequence](../../src/cli/xchandles/listen.rs#L360)). A crash or disk-full event can persist the registry tip but only part of its projections. On restart, resuming from that tip may omit the already-recorded transition, so replay is not a guaranteed repair mechanism.
5. **High — reorg recovery has replay gaps and does not survive reconnect/restart.** The recent header window is explicitly in-memory and starts empty for each connection ([window](../../src/cli/xchandles/listen.rs#L604)). After rollback the code calls non-detailed `sync_xchandles`, discarding canonical replacement transitions before freshness is restored ([reorg resync](../../src/cli/xchandles/listen.rs#L677)). The persisted resume path also has no visible canonical-header checkpoint validation ([resume logic](../../src/cli/xchandles/sync.rs#L57)).
6. **High for spend construction — `/neighbors` bypasses freshness.** The newer API routes call `require_fresh`, but the merged legacy `/neighbors` handler reads SQLite directly without that gate ([handler](../../src/cli/xchandles/listen.rs#L250)). The supplied Nginx file explicitly calls this endpoint “spend-critical” ([Nginx route](../../xchandles-api-nginx.conf#L178)), so it can serve stale proofs during startup, reconnect, or rollback even when other chain reads correctly return 503.
7. **Medium-high — API failure may not fail the process.** The server is detached with `tokio::spawn`; bind and serve use `unwrap`, so an address conflict/runtime server error panics only that task while the WebSocket/indexer loop continues ([spawn](../../src/cli/xchandles/listen.rs#L193), [server unwraps](../../src/cli/xchandles/listen.rs#L237)). Container restart policy will not help if the main process remains alive.
8. **Medium — reconnect behavior is minimal and readiness is optimistic during reconnect.** Errors use a fixed five-second delay without backoff/jitter, while clean close/EOF returns `Ok` and loops immediately ([outer reconnect](../../src/cli/xchandles/listen.rs#L199), [close handling](../../src/cli/xchandles/listen.rs#L830)). `begin_resync` is called only once before initial startup, not at the beginning of each connection cycle ([startup gate](../../src/cli/xchandles/listen.rs#L189)); after a disconnect, reads can continue appearing fresh until the 300-second age limit. There is also no application heartbeat/read timeout.
9. **Medium — health and observability are insufficient for unattended operation.** `/` and `/healthz` always return 200 and do not report readiness, indexed/upstream height, last success, resync/reorg status, or dependency health ([health handlers](../../src/cli/xchandles/listen.rs#L246), [health route](../../src/cli/xchandles/listener/api.rs#L115)). Logging is unstructured `println!/eprintln!`; there are no metrics, tracing, alert hooks, or documented backup/restore procedure.
10. **Medium — throughput headroom is unproven.** The listener fetches full block spends on relevant registry transitions and again for every tip, serializes database access through one process-wide mutex, and performs per-record JSON reads/writes ([tip work](../../src/cli/xchandles/listen.rs#L703), [shared DB state](../../src/cli/xchandles/listen.rs#L119)). No load, long-running soak, large-database, multi-registry, or Coinset fault-injection tests were found.

## Test evidence and recommendation

`cargo test --locked` passed on 2026-08-19: **88 tests total** (59 library unit tests and 29 real-HTTP integration tests; 0 failures). The integration fixture binds a real Axum server and validates golden response/error shapes ([fixture](../../tests/listener_http.rs#L56), [first contract test](../../tests/listener_http.rs#L202)). This gives good confidence in API semantics and in-memory reorg projection logic, but it does not run the production `xchandles_listen` loop against Coinset or test SQLite restart/crash consistency, socket reconnects, API bind failure, resource exhaustion, or sustained load.

Before rating it production-ready (8+/10), replay every detailed transition in live/reorg catch-up; map coin records by coin ID rather than response position; make projection updates transactional and error-propagating; freshness-gate `/neighbors`; persist and validate a canonical block checkpoint; supervise the HTTP task together with the listener; add bounded backoff/jitter plus heartbeat/timeouts; and expose readiness metrics. Add restart-during-write, skipped-multiple-spend, multi-launcher response reorder, reorg-during-downtime, disk-full, upstream-outage, and soak/load tests. Until then, use it only as a supervised/canary read API behind the supplied reverse proxy, with persistent storage, backups, and external checks against a chain-dependent endpoint—not only `/healthz`.
